# HILERA authentication threat model

Proposed for architecture, security and privacy review. The controls describe a future email/password build. The current frontend preview uses synthetic content and has no live accounts, authentication, protected records or database. See the [architecture](backend-authentication-architecture.md), [contracts](auth-api-contracts.md) and [decision register](auth-security-decisions.md).

## Scope and trust boundaries

- **Assets.** Email identity, transient plaintext passwords during submission, Argon2id credentials, session cookies and digests, CSRF and throttle keys, minimal security events, infrastructure secrets and future protected health records.
- **Adversaries.** Anonymous automated abuse, cross-origin web pages, a consumer trying to reach another account, anyone with a leaked credential, cookie, database backup or deployment secret, and compromised browser or server components.
- **Boundaries.** Browser input, headers, cookies and route parameters are untrusted. A trusted HTTPS ingress sanitizes forwarded headers. Node Server Actions and server-only services enforce identity, mutation and access rules. PostgreSQL is accessible only to authorized services and operators using separate runtime and migration privileges. Telemetry, backups and preview environments are separate boundaries. Review them before accepting real identity or health data.
- **Authority.** The request's active database session identifies its consumer principal. Future resource queries constrain ownership to that principal. The browser cannot assert a role, owner, eligibility or trusted health status. A Proxy or layout may assist navigation. DAL checks remain mandatory. [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication) · [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## Threat register

MVP mitigations below are proposed release controls. Future mitigations need the relevant product, security and privacy review.

| Threat | Impact | Proposed MVP mitigation | Possible future mitigation | Residual risk |
| --- | --- | --- | --- | --- |
| Password database or backup compromise | Offline password guessing, email disclosure and credential reuse against other services | Salted Argon2id with versioned parameters benchmarked at the approved security floor, restricted credential reads, encrypted and access-controlled backups, conditional rehash after successful verification | Tune work factor as hardware changes, consider a separately stored pepper with a recovery plan, add approved phishing-resistant authentication | Weak or reused passwords remain guessable. A live server compromise may capture passwords before hashing. |
| Credential stuffing | Account takeover using passwords leaked elsewhere | Shared PostgreSQL admission budgets before hashing, multi-key and service-wide pressure limits, generic errors and bounded security signals | Review breached-password screening, targeted step-up and phishing-resistant authentication | Low-volume distributed stuffing can resemble normal activity. Shared network sources limit attribution. |
| Brute-force login and password spraying | Guessed passwords, excessive Argon2id work, targeted or service-wide denial of service | Atomic short-lived counters, budget on normalized identity plus source or service load, cap concurrent hashes and request sizes, avoid an irreversible unauthenticated lockout | Review calibrated progressive challenges, incident detection and abuse capacity as traffic grows | Throttles can still affect legitimate users on a shared connection. A distributed attack can exhaust coarse capacity. |
| Account enumeration | Disclosure that a person has a HILERA account and improved targeting | Generic missing, incorrect and ineligible login results. Dummy verification for a missing credential after admission. Compare response shape, status, redirects, cookie/header differences and timing. Use generic duplicate-registration failures and rate controls. | Revisit sign-up/recovery UX once ownership verification and recovery policies are approved. Monitor systematic probing within the approved privacy scope. | Registration success or automatic login can differ observably from a duplicate. Generic failure can confuse legitimate users. Timing equivalence cannot be guaranteed. |
| Session fixation | Attacker supplies a token and retains access after the victim authenticates | Generate a fresh unpredictable token on successful authentication, invalidate or replace the presented active session where appropriate, and never promote a pre-auth token to a logged-in session | Review fresh authentication or rotation for future privilege and recovery transitions | A compromised client may observe the new token. Concurrent requests around rotation require testing. |
| Session theft | A stolen bearer gives access as the consumer | HTTPS, secure HttpOnly host-only cookie, no `Domain` or script-readable auth state, digest-only database storage, redacted request telemetry and server-side expiry and revocation | Approved account session management, anomaly detection and stronger authentication for sensitive actions | Browser extensions, malware or live server compromise can still steal a token. A current bearer remains usable until it expires or is revoked. |
| Session replay | An attacker repeats a captured bearer across browsers or after logout | Strict server validation on each protected operation, enforce idle and absolute expiry, retire a session on revocation or rotation, and issue cookies only after transaction success | Review revocation of related sessions and additional user proof for especially sensitive operations | An unexpired, unrevoked bearer can be replayed. A CSRF token protects a separate browser request threat. |
| Cross-site request forgery, including login CSRF | Unauthorized write or the victim being switched to an attacker-controlled account | POST-only mutations. Compare exact configured scheme, host and port. Use exact `Referer` origin only when `Origin` is absent. Reject malformed, `null` or unknown origin and reject when neither signal is usable. Use Next.js origin checks, `SameSite=Lax` and a domain-separated HMAC synchronizer token tied to the active session for authenticated writes. | Validate a short-lived pre-session token for anonymous forms if exact-origin enforcement cannot be relied on. Keep pre-session and authenticated session identities separate. | Browser and proxy behaviour must be verified. Same-origin XSS can act with the victim's session and access page-rendered CSRF tokens. |
| Cross-site scripting in an authenticated browser | Reading accessible health content and sending operations as the current user | Use React escaping, keep untrusted HTML out of templates, apply a tested restrictive Content Security Policy, minimize third-party scripts and DTO fields, and keep the auth cookie HttpOnly | Security-reviewed richer content pipeline, automated CSP regression and dependency checks | HttpOnly prevents direct script reads of the cookie. It cannot prevent malicious same-origin script from using it indirectly. |
| Insecure direct object reference | A consumer reads or changes another user's record by guessing an ID | Scope each sensitive query to both the object identifier and the session-derived owner. Use generic denial or not-found responses. Test with two distinct synthetic accounts. | Evaluate database row-level security as an independent defence when health schemas and tenancy rules exist | A future query that drops the ownership predicate can still expose records. Opaque identifiers alone offer no authorization. |
| Broken authorization or cache isolation | Authenticated or anonymous requests bypass UI checks, or one user's response is shared with another | Deny by default in the DAL for every sensitive read/write, including actions and direct requests. Use least-privilege DB credentials and no shared caching of personal data, HTML or RSC payloads. Avoid relying on Proxy, hidden links or a persistent layout. | Separate administrative authorization, independent authorization review and automated coverage of new routes | New transports, server components or cache settings can reintroduce bypasses. Browser history may retain previously displayed data. |
| Sensitive data in logs, tracing or analytics | Passwords, session secrets, identities or health data persist in a secondary system | Allowlist event fields. Remove request/response body, cookie, authorization and query capture across application, ingress, runtime, tracing and errors. Audit with synthetic canaries and restricted access. | Reviewed retention and privacy-preserving security monitoring with export controls | Infrastructure defaults and debug settings can capture data outside application code. Even minimal event patterns may be identifying. |
| Leaked environment secrets | Database or keyed-control compromise, unauthorized service access | Server-only secrets with least privilege and separate environments. Ignore real `.env` files, use placeholders in `.env.example`, and avoid exposing values through `NEXT_PUBLIC_` configuration, deployment logs or built assets. Review key rotation and datastore credential revocation. | Automated secret scanning, managed rotation and incident drills once infrastructure is chosen | Privileged operator or build-system compromise can still disclose values. Exposure can require service interruption and user-session revocation. |
| SQL injection | Credential disclosure, unauthorized mutations or database compromise | Parameterize values through Drizzle/node-postgres. Allowlist any dynamic SQL identifiers and operators, and review migration and raw SQL paths. Separate runtime, migration and operator privileges. | Add injection regression coverage for future queries and independent database hardening review | Unsafe raw SQL or elevated grants can defeat application protections. |
| Mass assignment | Consumer grants themselves privileges, changes ownership or bypasses state rules | Explicitly parse and validate the small request DTO. Reject unknown or repeated application fields. Assign user ID, roles, account status, state and session metadata inside trusted server logic. | Generate reviewed schema-bound contracts and maintain mutation-level authorization tests for new features | A future adapter that spreads raw form data into a write can bypass the original allowlist. |
| Insecure error messages | Database structure, account existence, credentials or health data leak to users and attackers | Map to public-safe categories. Keep generic credential failure and duplicate handling free of avoidable discrepancies. Strip stack, SQL, request and session details. Use opaque references for reviewed operator diagnostics. | Unified redaction validation and synthetic adversarial error injection | Proxy-generated errors or timing can expose detail if deployed defaults drift. |
| Stale, expired or revoked sessions | Continued access after logout, expiry, account change or device incident | Check the digest, account state, revocation and both expiry bounds on the server at each operation. Treat outage as fail-closed. Invalidate current session transactionally before clearing its cookie. For sensitive writes, define transaction boundaries that resolve revocation races. | Revocation drills, account-wide incident response and approved re-authentication policy | A response already delivered or request already committed cannot be recalled. In-flight races and cached browser content need explicit testing. |
| Concurrent sessions and multi-tab races | Unexpected sign-out, credential issuance races or a device retains access | Give every issued session its own token and revocation record. Recheck account and credential eligibility before issuance. Make revocation idempotent and avoid resurrecting expired sessions through activity updates. Keep device caps and all-device behaviour unresolved. | User-facing session management, reviewed device display and account-wide sign-out | Separate sessions remain usable until expiry or revocation. Concurrent token responses can race, and a shared browser may retain rendered data. |
| Account recovery abuse | Identity takeover by impersonation, replay, leaked reset proofs or support override | Keep the recovery operation and mechanism deferred. Do not treat an unverified address, support request or possession of a session as sufficient recovery proof. Reserve a server-only recovery boundary with no public mutation. | Review proof of identity, expiry and one-time use, abuse controls, generic responses, notifications, staff process and post-recovery session revocation before selecting a method | A locked-out user has no recovery path until a mechanism is approved and built. Attackers may seek support-channel workarounds. |
| Account deletion and lifecycle abuse | Unauthorized deletion, retained credentials, unrevoked access or improper disposal of sensitive records | No deletion workflow until approved. Design the data model to support revocation on approved disabling or deletion and avoid accidental health-record cascades. Require authenticated authorization and review lifecycle changes. | Approved confirmation and re-authentication, transaction and retry semantics, export/retention and backup deletion policy, auditable revocation | Physical retention in backups and asynchronous deletion can outlast access. Permanent deletion and identity reuse require product and privacy decisions. |
| Unverified email ownership and account squatting | A mistyped or intentionally reserved address blocks the rightful owner. Email-based downstream workflows may reach the wrong person. | Treat email solely as an identifier for password sign-in. Use uniqueness and no automatic merging or reassignment. Do not describe the address as verified or route sensitive account information or recovery to it. | Separately approved ownership verification, correction and support procedures with a safe migration path for existing accounts | Without ownership proof the rightful owner can be blocked or confused. This is a product and security release risk to review. |

## Security events and abuse data

Start with reviewed events such as account created, successful or failed login, logout and session revoked. Reserve password-change and recovery events for those future flows. Prefer event type, outcome, server timestamp and a bounded reason code. Store the user ID only where attribution is necessary and allowed. Failed attempts against unknown identities can use an absent user ID. Use an opaque request reference for correlation when justified. Access and retention require security and privacy review. [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

Rate state and security events have different purposes. Use shared atomic PostgreSQL counters with expiry for abuse admission. Avoid persisting raw emails, IP addresses, session IDs or device fingerprints for that purpose. A keyed, short-lived source or identifier key remains potentially identifying and needs review. Never record passwords, password hashes, cookies, session or CSRF tokens, health values, questionnaire answers, complete request bodies or unredacted exception data. Set production proxy and infrastructure logging explicitly and verify synthetic canary fields do not reach sinks.

## Verification priorities before handling protected data

1. Test duplicate sign-up races and rollback, safe hash migration, incorrect/unknown/ineligible login equivalence, issuance under concurrent credential change, session fixation and logout/revocation across requests.
2. Test expiry boundaries, shared counter concurrency, denial of service resilience, malformed and oversized input, injection and mass assignment, and safe failure when the session or throttle database is unavailable.
3. Exercise exact-origin, foreign-origin and same-site sibling-origin actions, present invalid versus absent `Origin`, exact `Referer` fallback, replay of an expired or rotated CSRF proof, and anonymous login/signup CSRF. Verify ingress strips spoofed forwarded headers.
4. Exercise the protected app routes through hard refresh, prefetch, direct action invocation and client navigation. Verify a second synthetic consumer cannot read or write another user's resources. Check responses and caches for cross-user disclosure, and inspect all log sinks for forbidden data.
5. Resolve launch policy before enabling real accounts. Record the owner decisions on password policy, immediate sign-in, idle and absolute lifetime, concurrent sessions, throttle behaviour, email ownership, recovery and account lifecycle. If a release proceeds without verification or recovery, document the accepted operational impact and its support boundary.
