# HILERA authentication production-readiness checklist

## Purpose

This checklist is the release gate for the first-party email-and-password authentication foundation implemented on draft PR #6. It does not authorize health-information persistence, document upload, clinical logic, email verification, recovery, or production exposure by itself.

A release item is not complete because code exists. The evidence must be recorded and reviewable.

## 1. Source and dependency integrity

- [ ] PR is reviewed, non-draft, mergeable, and contains only approved scope.
- [ ] Next.js is pinned to the reviewed security-patched release.
- [ ] eslint-config-next is aligned to the reviewed Next.js release.
- [ ] pnpm lockfile is regenerated by pnpm and frozen-install validation passes.
- [ ] Production dependency audit reports no unresolved critical/high advisory accepted by accident.
- [ ] Native Argon2 package and platform compatibility are verified on the intended runtime.
- [ ] No secret, credential, token, database URL, or real user/health data exists in Git history or tracked files.

## 2. PostgreSQL schema and migration

- [ ] Initial authentication migration replays successfully into an empty disposable PostgreSQL database.
- [ ] Generated SQL has been reviewed for destructive operations, locks, constraints, indexes, foreign keys and unintended cascades.
- [ ] Canonical email uniqueness is enforced at the database.
- [ ] Session token digests are unique and exactly 32 bytes.
- [ ] Session timestamp-order constraints are enforced.
- [ ] Runtime and migration credentials/roles are separate or the deployment exception is explicitly reviewed.
- [ ] Runtime connection pool and statement timeout are sized for the selected deployment.
- [ ] Production PostgreSQL version/provider/region are explicitly selected and reviewed before production deployment.

## 3. Backup and restore

- [ ] Synthetic pg_dump completes.
- [ ] The synthetic source database is destroyed.
- [ ] pg_restore succeeds into a new isolated database.
- [ ] Restored users, credentials, sessions and constraints pass integrity checks.
- [ ] Restore procedure explicitly invalidates or otherwise handles stale sessions before traffic resumes.
- [ ] Production automated backups are enabled before real identity or health data is entrusted to the database.
- [ ] Point-in-time recovery is enabled where the provider supports it.
- [ ] Backup failure monitoring exists.
- [ ] Backup retention, RPO and RTO are approved before launch.
- [ ] A periodic restore-test schedule and owner are assigned.

## 4. Authentication behavior

- [ ] Password policy is 15–128 Unicode code points with no arbitrary composition rule.
- [ ] Common/compromised-password blocking remains local/offline at runtime.
- [ ] Plaintext passwords and password hashes do not appear in logs or responses.
- [ ] Sign-up creates user, credential and initial session atomically.
- [ ] Successful sign-up routes to Onboarding.
- [ ] Successful sign-in routes to Overview.
- [ ] Unknown email and wrong password expose the same public-safe sign-in result.
- [ ] Duplicate sign-up never changes, merges or signs into the existing account.
- [ ] Email ownership is not implied by possession of the password.

## 5. Session and authorization

- [ ] Production cookie is __Host-hilera_session with Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain.
- [ ] Only the session bearer digest is stored.
- [ ] 1-hour idle expiry is enforced server-side.
- [ ] Explicit authenticated pointer/touch or non-repeated keyboard activity can renew idle expiry.
- [ ] Passive reads, direct navigation, RSC prefetch, timers and background work cannot renew idle expiry.
- [ ] Renewal writes are bounded and concurrent renewals are safe.
- [ ] 24-hour absolute expiry never moves.
- [ ] Expired/revoked sessions cannot be revived.
- [ ] Concurrent sessions behave as approved.
- [ ] Sign-out revokes the current server session before clearing the cookie.
- [ ] The internal account-wide revocation primitive is tested.
- [ ] Direct unauthenticated requests cannot receive protected content.
- [ ] Two synthetic users cannot cross account boundaries.

## 6. Mutation integrity and abuse resistance

- [ ] Exact trusted-origin validation works through the actual HTTPS ingress.
- [ ] Referer fallback occurs only when Origin is absent and is exact-origin checked.
- [ ] Session-bound CSRF protection works for authenticated writes.
- [ ] Invalid, malformed and foreign-origin requests fail closed.
- [ ] PostgreSQL admission occurs before Argon2 work.
- [ ] Progressive throttling expires and does not become permanent account lockout.
- [ ] Global and identity limits are tested under concurrency.
- [ ] Production throttle limits are explicitly configured rather than inheriting development values.
- [ ] Any future source/IP signal receives separate privacy and trusted-ingress review.

## 7. Secrets and deployment boundary

- [ ] Production HILERA_AUTH_ORIGIN is exact and HTTPS.
- [ ] CSRF and throttle HMAC keys are distinct, random, server-only and held in the approved secret manager.
- [ ] DATABASE_URL uses verified TLS according to the selected provider/runtime.
- [ ] Ingress prevents direct unintended access to the application origin where required.
- [ ] Forwarded Host/proto headers are sanitized/overwritten by trusted ingress.
- [ ] HSTS and other production transport/security headers are reviewed at the deployment boundary.
- [ ] Protected/personalized responses are not stored in shared public caches.

## 8. Observability and privacy

- [ ] Authentication success/failure, sign-out, session revocation and availability signals can be monitored without exposing passwords, tokens, raw health data or unnecessary identity data.
- [ ] Database availability, connection saturation, statement latency and backup status are monitored.
- [ ] HTTP error rate, latency and deployment health are monitored.
- [ ] Throttle saturation and unusual authentication-failure volume can trigger an operational alert.
- [ ] Logs/traces are tested with synthetic canaries for forbidden-value leakage.
- [ ] Security-event retention and authorized operator access are approved before production exposure.
- [ ] No raw session token, token digest, password, hash, CSRF token, cookie or database secret is logged.

## 9. Recovery and identity release gate

- [ ] A secure account-recovery mechanism is approved and implemented before normal real-user production launch, OR the Product Owner and security review explicitly accept and document the residual permanent-loss-of-access risk.
- [ ] Email ownership verification remains clearly deferred unless separately approved.
- [ ] Case handling for the email local part is reviewed before recovery/email verification so HILERA does not silently create an unsafe identity equivalence rule.

## 10. Final validation

- [ ] pnpm lint passes.
- [ ] pnpm typecheck passes.
- [ ] pnpm test passes with PostgreSQL-dependent tests executed rather than skipped.
- [ ] pnpm build passes.
- [ ] pnpm audit --prod result is reviewed.
- [ ] git diff --check passes.
- [ ] Browser QA passes for sign-up, sign-in, sign-out and protected navigation on representative desktop/mobile widths.
- [ ] Actual local synthetic flow passes: create account -> Onboarding -> Sign out -> Sign in -> Overview.
- [ ] Security/privacy review signs off remaining deployment-specific items.
- [ ] PR is explicitly approved before merge.

## Release boundary

Passing this checklist authorizes only the approved authentication foundation. It does not authorize storage of real health information, document uploads, OCR/extraction, clinical interpretation, diagnosis, treatment or medication functionality.

PRD Sync Status: Not required for this checklist. It operationalizes already approved authentication behavior.
