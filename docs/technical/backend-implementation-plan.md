# HILERA backend authentication implementation plan

The approved product direction is email/password through HILERA's own backend. The product owner approved the architecture foundation on 9 November 2026. This plan governs the authorized A–D backend implementation. The Product Owner approved the V1 password/session product policy and database-safety controls on 10 November 2026. Remaining implementation-level security/privacy gates are called out below. Decisions and dependencies are tracked in the [security decision register](auth-security-decisions.md). Consult the [architecture](backend-authentication-architecture.md), [data model](auth-data-model.md), [server contracts](auth-api-contracts.md) and [threat model](auth-threat-model.md) together when reviewing a change.

Use a single server-side implementation of the account, credential, session and authorization rules. The browser routes call that implementation through the reviewed transport. The proposed target is a Node.js runtime for the existing Next.js app with PostgreSQL and Drizzle over node-postgres. Use synthetic fixtures throughout development and staging. A local PostgreSQL install or container is the standard development and restore-drill target; it must not be treated as the production backup destination. Production database backup, restore, and migration safety are governed by [database safety and backup](database-safety-backup.md).

## Delivery bundles

| Bundle | Deliverable and dependencies | Verification before review |
| --- | --- | --- |
| **A · Database and migrations** | Define the identity and credential tables from the approved subset of the [data model](auth-data-model.md). Write reviewable PostgreSQL migrations and server-only repositories. Establish separate local/test/production configuration, local synthetic fixtures, and the approved backup/restore safety controls. Requires architecture review, approved canonical email behaviour, compatible Node and PostgreSQL versions, runtime/migration roles and secrets handling. | Apply the migrations to an empty disposable local database, create a synthetic-data backup, destroy the disposable database, restore the backup, and verify integrity. Rehearse upgrading from a representative prior schema when one exists. Verify uniqueness, foreign keys, defaults, rollback or documented forward repair, least-privilege runtime access, and that request/SQL logging omits sensitive bind values. |
| **B · Credentials, sign-up and sign-in** | Implement a bounded Argon2id adapter, normalized identity lookup, atomic sign-up and generic sign-in outcomes in server modules. Enforce the approved 15–128 character password policy without arbitrary composition rules; apply the approved local/common-compromised-password blocking approach without sending plaintext passwords externally. Successful sign-up creates a session and routes to Onboarding; successful sign-in routes to Overview. Depends on A, reviewed Argon2id parameters and candidate runtime compatibility. Keep the transport closed to untrusted traffic while C and D are incomplete. | Check valid/invalid verification, fresh salts, encoding, rehash, maximum input/resource limits, nonexistent-user handling, duplicate normalization and concurrent signup, transaction failure and concurrent credential change. Benchmark verification on the intended runtime before choosing capacity and configuration. |
| **C · Sessions, cookie, sign-out and route protection** | Add opaque session rows, expiry and revocation, host-only cookies, server-side session/user guards, narrow user responses and authorization-scoped queries. Enforce the approved 1-hour idle timeout, 24-hour absolute lifetime, concurrent sessions, current-session logout, and reusable account-wide revocation primitive for future password change/recovery/deletion. Wire the approved browser actions and protect the six `/app` surfaces when serving an authenticated deployment. Requires B and a deployment origin capable of same-origin TLS. | Cover cookie properties and fresh token issuance, fixation, replay, expiry, cross-user reads/writes, protected direct requests, logout with multiple tabs, cookie-only clearing, safe redirects, session-store failure and cross-origin state changes. Exercise server actions and any Route Handlers directly as well as through the UI. |
| **D · Abuse controls, minimal events and hardened responses** | Implement shared bounded PostgreSQL counters with admission before expensive hashing, generic public-safe credential failures, temporary progressive throttling without permanent account lockout, and minimal allowlisted security events. Bring response/trace/log redaction and event retention into the same review. Depends on A–C; exact numeric throttling thresholds/windows and privacy-sensitive source signals remain implementation-level security/privacy review items. | Send concurrent attempts through multiple application instances. Check counter correctness, saturation, cleanup, throttling recovery, bucket-store failure, generic error parity and lack of durable lockout from a public request flood. Test that untrusted forwarded headers cannot bypass the chosen policy. Inspect response bodies and logs under success, auth failure and dependency failure. |
| **E · Recovery** | Design and implement only after the recovery method, abuse and enumeration controls, identity proof, recovery communications, credential replacement and session revocation are explicitly approved. Update threat and contract docs before implementation. | Build mechanism-specific tests for expiry/replay, one-time consumption where applicable, account takeover, recovery enumeration, abuse, credential change races, session revocation and notifications once the mechanism exists. |

The fastest safe delivery path is a single branch for A–D with reviewable migration and security checkpoints. Review the A schema early. Build B and C together once the credential and session policies are ready. Start D alongside the login service so every credential path has bounded admission and consistent errors before wiring live traffic. Release A–D together after the shared acceptance gates pass. E remains a separate decision and delivery bundle. If recovery is still absent, product and security owners must explicitly resolve the launch consequence for users who lose a password.

## Required acceptance and regression coverage

These are future release requirements. Run lint, type checking, the repository unit suite, production build, a disposable PostgreSQL integration suite and browser end-to-end tests in the implementation work. If integration or browser infrastructure is absent, create it in that implementation or record the gate as unmet. Avoid real patient or account data.

| Acceptance criterion | What to demonstrate |
| --- | --- |
| **No plaintext credential persistence** | Create accounts using synthetic secrets and inspect persisted rows, events, trace captures and background payloads. Only an approved encoded credential representation remains. Scan client payloads and server diagnostics for leakage. |
| **Approved password hashing** | Assert the Argon2id encoded algorithm and approved parameters. Verify different salts for two equal passwords, successful validation, invalid-secret rejection and safe upgrade from a previously accepted hash. Use controlled parameters and load tests for runtime resource bounds. |
| **Duplicate identity handled safely** | Exercise policy-defined normalization variants, case/Unicode boundaries and parallel requests for one canonical address. At most one account/credential is created. No merge, overwrite, orphan credential or existing session issuance occurs from the duplicate request. Check approved public response semantics and document any observable sign-up enumeration trade-off. |
| **Valid revocable session on sign-in** | Successful sign-in commits an owned session and returns the expected cookie and approved next route. The database contains only the digest. An incoming cookie cannot choose the new bearer. Failed or rolled-back issuance produces no valid cookie. |
| **Unauthenticated access denied** | Exercise direct requests to dashboard, add measurement, history, trends, risk summary and education. Follow the approved unauthenticated response and confirm protected rendering/data is absent in HTML, serialized server component output and cached responses. Check direct calls to guarded actions/handlers. |
| **Users access only their own data** | Use two synthetic consumers. Change user/resource identifiers in requests and test reads, writes and list queries. Verify the server derives the user from its session and filters access at the data layer. Use approved auth-owned fixtures or a test-only owned resource if no health data feature exists. |
| **Logout revokes on the server** | Save an issued synthetic bearer for an authorized test, sign out, and replay it from another browser context. Rejection confirms revocation independently of cookie deletion. Check repeated sign-out and store failure without false success. |
| **Expired or revoked sessions rejected** | Use a controlled clock to test idle and absolute boundaries and expiry despite repeated activity. Race renewal and revocation and check that the old bearer never revives. Test the approved concurrent-session behaviour and credential-revocation races. |
| **Generic sign-in failures** | Compare wrong-password and unknown-account responses across status, body, headers and redirects. Sample timing under controlled conditions to detect a practical enumeration shortcut. Internal failures remain public-safe and diagnosable through scrubbed server-side signals. |
| **Throttling is testable** | Set test-only limits and a controllable clock. Test affected scopes, multiple instances, atomic reservations, bounded counter cardinality, sustained traffic and temporary restrictions expiring. Check shared-network and targeted denial-of-service behaviour against the approved policy. |
| **CSRF controls work** | Verify approved same-origin mutations and rejection for cross-site or untrusted origins, including login and logout. Test missing/mismatched origin or fallback rules, proxy spoofing assumptions and required token checks. Confirm safe methods do not perform user-requested state changes and cross-site requests cannot extend sessions. [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) |
| **SQL injection and mass assignment blocked** | Inspect query construction for bind parameters and add adversarial identity/ID inputs. Attempt to set server-owned fields through extra input keys. Validate that typed access does not interpolate raw SQL or broaden ownership. |
| **No auth secrets or raw health data logged** | Review application, proxy, platform, database and error reporting on representative success and failure paths. Assert logs, traces and emitted events omit passwords, hashes, tokens, cookies, DSNs, raw health values and questionnaire answers. Verify events contain only approved fields. |
| **Reviewable migration and recovery** | Review SQL, names, grants, indexes, transaction locks and affected entities in the PR. Rehearse rollback where practical, or document a tested forward-fix and restore procedure for data changes. Include how restores avoid reactivating revoked sessions. |
| **Browser and transport guardrails** | Verify `Secure`, `HttpOnly`, host-only `__Host-` prefix rules, `SameSite` and path under HTTPS. Test before hydration and with scripts unavailable. Credentials must reach only a validated POST, with no fallback submission that puts them in a URL. Confirm no protected shared caching, untrusted redirect, browser storage of bearer state, or public preview connection to a real identity store. [Next.js Authentication Guide](https://nextjs.org/docs/app/guides/authentication), [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) |

## Release gates

1. **Complete the remaining implementation-level security and privacy review.** Product implementation authorization for A–D is approved. Complete security/privacy review for the final Argon2id profile, threat model, authorization boundaries, logging/retention, abuse-control thresholds, qualifying idle-renewal activity, and cookie/origin assumptions. Email ownership verification and recovery remain deferred and must not be added by implication. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
2. **Review migrations and contracts before rollout.** Inspect generated SQL, application and migration role grants, compatibility across versions, failure handling and data preservation. Pin reviewed dependencies. Confirm the selected Argon2id implementation packages for the target runtime, then benchmark under concurrent requests. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
3. **Verify the complete flow in isolated HTTPS staging.** Use the same approved runtime and proxy assumptions with isolated credentials and synthetic fixtures. Run the full acceptance suite across multiple instances. Review the error and abuse budget with production-like traffic. Verify automated backup configuration for the selected production database platform, point-in-time recovery where supported, alerting on backup failure, and a documented restore procedure. Rehearse restore using synthetic or approved sanitized data only.
4. **Release A–D behind a deliberate exposure gate.** Disable or contain public entry until all controls are operational. Require sign-off on the runbooks for revocation, database outage, abuse saturation, accidental leakage and migration recovery. Record the deploy order, rollback decision point, audit retention and restricted incident access. Do not expose the system as a real-user production health account experience until secure account recovery is implemented or the Product Owner and security review explicitly accept the residual loss-of-access risk. The static testing preview serves synthetic data and cannot run the Node.js authentication path.
5. **Release later mechanisms independently.** Recovery, verification, new account lifecycle transitions, administration and future health-data tables each need their own scope and security review.

## Open product decisions

| Decision | What must be resolved before exposure | Likely PRD impact if approved |
| --- | --- | --- |
| Exact password policy | Permitted length and character handling, strength and blocklist requirements, user-facing messages. Technical request and hashing limits still need security review. | Password and account behaviour. |
| Email identity behaviour | Canonical address syntax and equality, local-part case, internationalized addresses, duplicate registration response and any display form. | User-facing identity, accepted identifiers and conflict journey. |
| Immediate sign-in after sign-up | Whether account creation issues a session and where the user lands. Resolve the existing product-state route after sign-in and behavior for a failed issuance. | Sign-up and sign-in journey. |
| Idle and absolute session lifetimes | Exact durations, qualifying activity, renewals, user-visible expiry and any reauthentication requirements. | Session behaviour and interruption of user journeys. |
| Concurrent sessions and revocation | Whether multiple sessions are permitted, and rules for logout, credential replacement and compromised sessions. | Account and session behaviour. |
| Failed-login limits and response | Thresholds, cooldown/backoff, scopes, user messages and safeguards against targeted account denial. | Authentication behaviour if it affects user attempts, lockouts or support. |
| Recovery method | Identity proof, recovery controls and timing relative to initial release. | Recovery journey, communications, collection and permissions. |
| Email verification timing | Whether and when to add ownership verification and the implications of deferred verification on messaging and recovery. | Signup requirements, identifier trust and communications. |
| Account deletion and retention | Entry point, confirmation/re-authentication, immediate revocation, deletion scope, backups and event retention. | Account lifecycle, user controls and data retention. |
| Security-event data | Approved actor linkage, retention, access and whether any network/device input is justified. | Privacy or data-collection requirements if new personal data or uses are approved. |

**PRD Sync Status — Not required for this architecture document.** Approved changes to authentication behaviour, account lifecycle, data collection or user journeys must be assessed for sync by product governance before implementation. Internal schema, transport, infrastructure and security settings belong in technical documentation when they preserve those requirements.
